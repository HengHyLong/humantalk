# v2.6 数字人问答分流

## 数字人前端访问密码

前端启动前必须通过服务端密码验证，初始密码为 `10528`。后台“系统管理 → 模型管理 → 数字人前端访问密码”可以修改密码（5–128 字符），需要 `system:llm:write` 权限。密码以 Argon2 哈希保存在管理数据库的 `frontend_access` 表中，不回传密码或哈希。修改后旧浏览器验证立即失效，前端在重新打开、聚焦或每分钟检查时返回验证页。

验证使用 HttpOnly、SameSite=Lax 浏览器会话 Cookie，不设置固定到期时间、Max-Age 或 Expires。浏览器会话内刷新或重新打开页面无需再登录，浏览器正常退出后重新验证。启用浏览器“恢复上次会话”时，浏览器可能恢复会话 Cookie；网站无法可靠获知浏览器进程退出，此场景需关闭浏览器的会话恢复或启用退出时清理 Cookie。升级会拒绝旧版 12 小时 Cookie，需要重新验证一次。数字人 HTTP、SSE、WebSocket 接口由服务端校验；管理员沿用管理员登录和权限管理，可访问数字人调试接口。公开展品登记二维码接口及 `/healthz` 保持可用。运维健康检查应使用 `/healthz`；调用数字人接口前先请求 `POST /frontend-access/login`，保存返回的 Cookie。`GET /frontend-access/status` 查询验证状态，`POST /frontend-access/logout` 清除当前浏览器验证。`GET/PUT /api/v1/admin/frontend-access` 查询或修改密码，需要对应管理员权限。

## 空回答与自动重试

后台“Dify 数字人问答”可设置最大追加重试次数（0–3，默认 3；0 关闭）及整轮重试时间预算（5–180 秒，默认 30）。首次请求加最多三次追加重试，退避约 0.5、1、2 秒并加入少量随机延迟；HTTP 429 等响应的 `Retry-After` 优先。时间预算覆盖生成和退避，预算耗尽会提前结束，停止上游任务的清理最多额外等待 2 秒。单次请求还受“回答超时”限制。

收到 `message_end` 后仍须校验可播报的最终文本。空白、纯思考、纯注释或纯标点不算有效答案。空回答、缺少结束事件、网络/超时错误、HTTP 408/429/5xx 可重试；认证、配置及其他 HTTP 4xx 错误不重试。达到次数或时间上限且未提交语音句子时，只播报一次“问答功能暂不可用，请联系现场工作人员。”，不再调用 OpenTalking 大模型。

每次尝试使用独立 HTTP 客户端与分句缓冲，沿用本轮输入和此前成功的会话 ID，失败片段不会混入下一次答案。只要一个句子已经提交给播报任务，就停止从头重试；后续失败按既有部分回答中断流程处理。完整回答模式也使用重试。新问题、关闭会话及过期轮次会取消请求和退避，不播放旧问题的失败提示。应用只保存成功答案的正常上下文；Dify 自己的日志可能保留失败尝试。

命中记录新增 `difyAttemptCount`、`difyAttempts`，逐次记录状态、耗时、安全错误码、HTTP 状态、会话/消息/任务 ID、退避及终止原因。数据库直答为零次。环境变量分别为 `OPENTALKING_DIFY_CHAT_MAX_RETRIES` 和 `OPENTALKING_DIFY_CHAT_RETRY_BUDGET_SEC`，无需改动 Dify 的提示词或模型即可生效。

## 完整句子流式播报

后台“系统管理 → 模型管理 → Dify 数字人问答”可选择“完整句子流式播报”或“完整回答后播报（回退模式）”。开关下一轮生效，不中断正在播报的回答。环境变量 `OPENTALKING_DIFY_CHAT_SPEECH_MODE` 取 `sentences` 或 `complete`，代码默认 `complete`；上线时可显式启用 `sentences`。

分句模式只对 Dify 回答且支持持续直接播报的数字人生效；数据库直答保持原方式，Vidu 及其他不支持的驱动自动回退。请求可传 `speech_mode=complete` 单轮回退，全局回退时请求不能强行启用流式。

Dify 文本通过增量过滤后，仅完整句子进入同一直接播报任务，不经过 OpenTalking 大模型。只有收到 `message_end` 才提交无标点尾句。句子通道限制 16000 字、256 段、10 分钟保留时间，TTS 队列上限 4 段。新提问和关闭会话停止旧生成与播报；每段按轮次校验，过期内容不能继续播放。

现有 HTTP 接口仍返回最终完整答案，SSE 新增 `qa.delta`（已提交句子的累计文本）、`qa.completed`（生成结束及计时）、`qa.replace`（正在更正）、`qa.error`（部分回答失败）。事件带 `turn_id`；生成文本先保存在前端，聊天文字与口播字幕随播报片段逐句推进；HTTP 最终结果和生成完成事件不会在播报开始前抢先展示全文。播报结束后补齐完整回答。SSE 短暂断开后，HTTP 最终结果保留用于补齐，不重启播报。`speech.ended` 才表示音视频播报结束，不能把 `qa.completed` 当成播报结束。

`message_replace` 会取消未播内容，并在完整替换答案到齐后以更正提示播报；已播放内容无法撤回。断流或语音异常明确提示未完成，不从头自动重播。响应新增 `speech_mode`；命中日志记录 `firstDeltaMs`、`firstSentenceMs`、`generationMs`。首句保持自然句末边界，不使用超时强切半句话。首句到齐即进入 TTS，不等生成完成；PCM 首音频窗口到齐即进入口型模型，不等整句合成结束。事件 `speech.synthesis_started` 和 `speech.lip_sync_started` 标记本轮首次语音合成和口型请求，可与 `qa.completed`、真实 WebRTC 首音频计时核对。

前端将文字、语音识别结果和实体卡片选择提交到 `POST /exhibitions/{exhibition_id}/qa/query`。后端按当前展会筛选可用的展商、展品和路线，统一决定回答来源。保留已有公开接口对草稿资料的可用规则，不改变资料状态；下线、停用和删除的资料不参与匹配。

- 明确、唯一的关键词命中：直接使用数据库播报文案或介绍。位置问题读取展位、地址；路线问题读取配置的播报文案或路线说明。返回 `match_type=database`，不调用 Dify。
- 未命中、模糊匹配、重名或缺少所需内容：调用 Dify 应用，并传递查询结果供智能体参考。普通问答返回 `match_type=dify`，重名返回 `clarification`。
- 两种回答都通过 `direct=true` 交给数字人 TTS 和口型驱动，不经过 OpenTalking 内置对话模型。Dify 不可用时播报固定服务提示。

后台“系统管理 → 模型管理”配置应用 Base URL、API Key、超时和候选数量，并测试连接。API Key 只保存在服务端环境文件，不回传给前端。展商、展品和路线的关键词、别名、介绍和播报文案继续在展会管理维护。

环境变量为 `OPENTALKING_DIFY_CHAT_BASE_URL`、`OPENTALKING_DIFY_CHAT_API_KEY`、`OPENTALKING_DIFY_CHAT_TIMEOUT_SEC`、`OPENTALKING_DIFY_CHAT_TOP_K`。应用凭据与旧版 Dify 数据集检索凭据独立。

Dify 使用对话应用或 Chatflow；配置可选输入 `exhibition_id`、`locale`、`retrieval_status`、`retrieval_context`。最后一个变量是 JSON，包含当前数据库事实。提示词应优先使用当前事实，缺少资料时说明或追问。答案节点输出最终回答文本，推理过程应分离。

同一会话保存 Dify conversation ID 和最近实体选择。数据库直接回答保留原 conversation ID；后续 Dify 请求继续该对话并接收当前事实。新提问、打断或关闭会话会撤销旧任务，过期回答不能重新进入播报队列。

## 匹配、起点和追问规则

编号完整匹配，允许 `S-01`、`S01`、`S_01` 的等价写法，但不命中 `S010`。纯数字仅在独立输入或展位、编号、型号上下文中识别，`02` 不会命中 `CNCC2026`。否定对象不作为候选；长名称只覆盖同一位置的短别名，独立提到的对象全部保留。

数据库直接回答要求：完整命中、意图属于介绍/位置/列表/有效路线、所需事实完整、无歧义或截断。价格、成立时间、比较、优缺点、复合问题、日程、模糊匹配、缺少答案字段和英文翻译交给 Dify。完整列表可直接播报；超过上限向 Dify 标记部分结果及总数。

后台展会工作台维护导航配置。数字人是固定终端设备，“怎么去 XX”默认查询后台明确命名为“终端至/到 XX”的路线，直接采用其播报说明和图片，起点显示为“终端”，目的地来自路线声明。路径点位是路线中的途经点，不作为终端路线的准入条件。用户明确指定其他起点或继续上一段行程时，按起点和路径点位匹配对应路线，不反转或拼接。终端路线多条且没有唯一默认项时需要选择；缺少路线或文案时按既有回退处理。

追问优先级：新名称/编号或更正、有效序号、唯一对象代词。卡片与缓存顺序一致，路线另存路线 ID。多个候选后的“它”不默认选择。登记请求仅在唯一展品且存在真实调研入口时返回 `registration`，前端生成二维码；无入口时提示咨询工作人员。

响应新增 `routing_reason`、`registration`。Dify JSON 上下文新增 `current_exhibition`、`intent`、`routing_reason`、`truncated`、`origin_id`、`destination_id`。命中记录包含匹配字段/关键词、分流原因、实体/路线 ID、起终点，便于追溯。

## 数据校验与 Dify 提示词

`POST /api/v1/admin/event/exhibitions/{id}/runtime-config/validate` 返回 `issues`：路线结构/名称/播报冲突、缺少终端起点、点位未关联实体、重复关键词和图片标记。新建及修改路线时拦截结构与已识别终点冲突。图片标记仅在播报时清理，原数据及图片保留。不能凭事实确定的路线终点和展品归属不自动改写，应按审计结果核对。

规则模板在 `configs/prompts/dify_exhibition_v26.txt`，需同步到生产 Dify 的 LLM 系统提示词并发布。四个可选输入保持兼容。提示词由 Dify 统一管理，后台原数字人角色提示词不进入此问答链路；知识库“待核验”资料不能覆盖本轮数据库事实。发布前备份工作流。

展商 → 展品 → 二维码流程由后端保存当前展会、当前会话的追问阶段。唯一展商数据库介绍完成后，存在可用关联展品才询问是否了解展品；明确确认后展示该展商的展品卡片。用户点击展品或说有效序号后介绍展品；仅存在已配置登记链接时询问是否需要二维码，再确认才返回真实二维码路径。拒绝或另问问题退出当前追问，多候选代词和越界序号继续询问选择。响应 follow_up 字段提供追问阶段和有效候选顺序，用于展示相应快捷回复。

导航追问支持“从终端出发”“从这里出发”，沿用尚待起点或上次已确认路线的目的地。导航请求展示路线及其图片，不以目的地点位介绍卡片代替路线弹窗。
